# Round 6：受控回调异常的静态定位

本报告仅做静态与历史协议分析，没有操作 DOS 桥。证据均来自同一 EMPEROR 原始重定位镜像，片段保存在本目录。

## 已确定的入口差异

round5 probe.call 直接调用 `4967E(W, source, result)`。当 W.state 为 FF、source=W+8 时，原函数 496B2 先将 state 设 FE，496D0 经 W.vtable+30 调用 3E245。3E245 将提示+8写FF，再调用307D2提示关闭。

然而正常提示事件并不直接从4967E开始：

* 提示 vtable=C1A78，+24 指向3039C。
* 3039C..307AC 的显式参数只有提示 self。提示+6为u16事件状态，不需要额外事件记录。
* global C3926=0 且提示+47为3或4时，303D5先清提示+58，303E8调用22552(CCD7C,提示+A)，30408再调用提示+12 owner 的 vtable+2C。
* 普通提示+6=3从3045A到306DF，先清+58，再移除窗口，最后3071B调用owner+2C；+6=4走30726，亦先移除并清+58再调用owner。
* 307D2发现提示+58=1，会先22552移除，再使用提示+A的对象+4与vtable+1C；发现+58=0则跳过移除。

因此直接owner回调遗漏了真实提示的事件前处理。它使window/focus链的移除发生在不同顺序，并且正常入口与受控入口调用307D2时的+58不同。这是具体可检验的异常原因；仅凭静态代码不能确认22552之后哪一对象已被释放，不能把“已证实释放后使用”写成事实。应在新DOS进程中对比原3039C入口与直接4967E入口，断点303E8、30408、307F2、3084A，保存提示+A、窗口vtable、shown标记及每次删除后的值。

## 修复测试驱动

对已经原构造并显示的提示，调用完整原3039C([message])，让原函数承担清shown、移除、通知owner。普通提示选择确定时将真实事件状态+6设3（仍属于受控输入）；slot3/4在C3926=0时无需事件状态。禁止用“仅改+58=0”冒充正常事件。

固定合成栈2B5000处于round5实际主循环ESP2B5528以下，相差1320字节。4967E的固定局部0x258亦向下生长，未直接覆盖主循环上方活动帧。深层调用范围、栈下限和旧帧引用仍须动态核实。由于整个probe.call不恢复原寄存器且留在sentinel，后续不得将sentinel当真实主循环上下文；恢复main时保存并恢复原栈内容、所有寄存器/flags，或直接采用真正事件循环。

## 其他选择对象的原入口

以下都是原控件事件函数，可用真实子按钮地址调用，避免跳过控件自身的数据同步。

|对象|原入口与参数|字段/行为|
|---|---|---|
|W+10普通菜单|86468(menu,button)|按钮数组+A+4*i；关闭按钮+26→FF；owner+2E；选项数+34|
|W+28国家选择|2A987(selector,button)|按钮数组+46+4*i；数目+C6；返回国家映射字节+A+i；owner+C2|
|W+1C兵员|27396(dialog,u32(dialog+1A))|确认从编辑对象+A/E/12/16的+43读取人数/头盔/甲/盾，自行写CC5F8..CC608；防御+1E，兵种+20；owner+32|
|W+14确认框|291A7(confirm,u32(confirm+A))|返回1；owner+12；仅此函数未找到取消0入口|
|W+3E选将|71E07(picker,u32(picker+4A+4*i))|数目+B2；模式+B0；owner+AE；原函数挑真实官员、写CCA74并以person.byte1通知owner|

选将模式1（7288E）筛掉状态4和特定职务后计可选择序号；模式2（7296C）直接沿链第i人。原返回77是职务字段，不是应直接作为数组button index的值。应从当前页合法显示按钮选择，不能把77硬作为picker索引。

确认框取消0尚未定位；291FA是程序关闭窗，不通知owner。需要沿真实窗口退出/取消事件追踪，不应调用291FA并人为补owner回调后宣称完整端到端。

## 历史证据限制

round5 exit-menu-retry-protocol开头已在F000:CA60/CA64实模式循环，不能当作第二次独立复现原protected-mode调用。历史LOGCPU尾部只是绘制拷贝，不能证明invalid opcode发生位置。新进程重跑与第一条异常指令捕获仍是必要验证。
