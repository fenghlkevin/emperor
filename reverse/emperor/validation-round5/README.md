# 第五轮：特殊标记来源、原菜单建战与关联255/256

分析对象为原始 EMPEROR.EXE；KING、QUICK的计数器实现另做静态交叉核对。动态测试运行于官方DOSBox-X的32位DOS/4GW内，使用复制的游戏目录。没有修改原安装包、原存档或原EXE。下文明确区分正常代码路径、受控输入、完整原函数返回及尚未通过的界面流程。

## 本轮确认

### 特殊标记 unit+17

[完整创建调用树](flag-origin/README.md)补齐了主动出征的 `4967E → 84210 → 84457`、自动入侵 `80BF6 → 84210 → 8437E`、主帅、地方兵、敌军、装备防御和援军的全部已定位建队函数。它们的显式字段写入均未覆盖unit+17；防御word只覆盖+15..+16。先前只测初始器的范围不足，本轮已扩大到菜单确认主帅后的最终建队。

原菜单动态过程：构造真实官员场景和战争菜单，选择主动出征、国家10、编队100兵及各100件装备，确认不再加队、选择闲散官员（返回值77）。均执行完整原 `4967E`，由原malloc分配B及节点，原 `84457`建成双方部队，原程序把节点加入全局链表，计数从0变1。场景11、对话框绑定数值及选择结果由调试器提供，因此这是DOS原菜单回调验证，**不是鼠标从宫殿点击的全流程证明**。

在原malloc刚返回、初始器尚未执行时，90个特殊字节的实测集合为 `{0,127,128,133,156,255}`。原内存快照为 `runtime/checks/battle-at-malloc.bin`。随后把90字节设成A5作为受控毒值，首次编队后90/90保留，确认主帅并完成84457后也90/90保留，快照为 `runtime/checks/battle-after-menu.bin`。这不是原游戏默认值；它说明在被执行的创建路径上没有把该字段初始化成某个业务状态。独立调用完整8437E自动建队及8454C援军入口，同样保留90/90毒值，见 `runtime/flag-auto.json`。原存档加载直接读入两组810字节，明确恢复该字节，第四轮已验证保存/加载往返。

综合证据支持 **unit+17是创建时未初始化、读档时原样恢复的字段**，值恰为1时启用85%损失系数。还不能给它命名为伏兵、守备或计谋，也没有找到正常建队主动赋1的业务分支。快照一致不能排除中间写入再恢复；不能以限定静态搜索排除所有任意别名或越界写。

监视器说明：首次BPPM试验在下一条49DB7即停，监视列表对许多地址显示00，而同地址MEMDUMPBIN仍为A5。这个监视配置不能当作原程序写标记的证据，本轮弃用其写入命中结论，采用原函数前后快照和完整静态写集合。请求及响应均保留在runtime/queue2。

### 关联序号的正常累计条件

[三版本计数生命周期和可达模型](association-reach/README.md)：从存档计数c0开始，A次确认主动出征、D次已生成属地受袭后，计数为 `(c0+A+2D) mod 65536`。主动出战每次分配1个，本地防守分配2个；取消菜单、普通队伍行动、战后释放不递增。保存和加载保留整个u16，正常结算没有直接归零该计数，也没有清除官员byte关联历史。

从0开始，第256次关联分配取255，第257次取256。128次属地受袭分配到254/255；255次主动出征后的一次受袭可在同场分配255/256。累计序号与同时存在战斗数、官员数、45个单位槽无关。原菜单已实际确认一次0→1；未通过自然游玩257次，也未证明资源、外交、寿命约束下每种重复开战方案都可持续达到边界。

### 255/256实际结算影响

`runtime/association-effect.json`执行原80D2B..80D59关联分配、原6670E查找、原667C0空节点读取及原667C2状态写入。`runtime/association-full.json`进一步执行**完整6668F原结算函数**，两例均返回原调用端。受控条件：两个真实存档官员，第二个经原分配块被选为出战者；第一个状态人为设7以观察是否被误改；非本地、退出理由1，军队空槽按原FF编码，使用真实原历史对象。

|序号|官员byte / 战斗word|原查找|完整6668F后的官员状态（首个/实际出战者）|实测结果|
|---|---|---|---|---|
|255|255 / 255|错配链首默认FF官员|0 / 4|无关官员被恢复，实际出战者仍滞留出战状态|
|256|0 / 256|node=0|7 / 4|没有恢复实际出战者，完整原结算仍返回|

256的原 `mov eax,[eax]` 在EAX=0时实测读出 `0xF000CA60`，随后原指令向 `0xF000CA62` 写byte0，且到达6680A。该DOS环境中没有因此立即退出；没有证明这个未映射/高地址写入持久损坏了其他有效游戏对象。不能将其描述为必然SIG、必然崩溃或正确恢复。吞并、删除官员等其他结算分支可能在后续free/链表操作产生不同影响，此处实际验证的是理由1的完整结算。

## 界面流程边界

[完整原菜单、战场及退出静态路线](menu-flow/README.md)已定位。正常主循环对象A=C98D8，保存控制器C=C9920，两者不同。真实战争窗口须先建立官员场景的CC5A0；直接从宫殿构造战争菜单缺少父对象，不能作为合法流程夹具。

本轮两次原菜单成功创建节点。确认出征后的提示关闭回调，测试出现DOS/4GW error2001、invalid opcode，画面见 `runtime/captures/command_001.png`。再恢复原主循环上下文后重试仍出现同类错误。错误发生在受控界面回调/焦点对象生命周期路径，未归因为正常游戏缺陷，也没有拿这次退出当作战后清理成功。

原菜单建战已通过；从宫殿实际点击、出征提示正常关闭、自然进入战场、真实行动得出战果再退出的**单次端到端UI流程仍未通过**。单独的完整结算函数通过不能替代这项要求。再次尝试在同一调试运行中把菜单创建接到战场退出时，确认主帅回调在15秒及追加30秒内未返回，CPU进入16位/实模式上下文，尚未执行后续战场构造和退出；见runtime/battle-exit-full.json。该状态下旧保护模式selector对象读数不可信，已从结果中撤下。不得用这份失败记录或静态路线冒充动态通过。
