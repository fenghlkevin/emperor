# 出战关联序号的正常累计与失配影响

本目录独立检查全部三个 EXE 的直接引用、LE 对象映射、原始存档和结算控制流；未操作 DOS debugger。本轮静态证据由 extract.py 可重复导出，动态主线结果另见上级报告。

三版本各恰好11条直接引用：3次取低byte、3次取word、3次word递增、存读各1次取地址。计数位于第二LE对象的未初始化虚拟区域，初始化页导出仅106496字节，而计数偏移超过该长度，不能拿截断导出空字符串当初始化值。原KING1/KING2存档计数0，KING3为2；原加载和保存每次明确传长度2。重开旧档恢复其计数，不是将所有局部计数清零。没有找到直接重置；这一结论严格限定直接引用及已经追踪的创建、结算、存读路径，不能用全文直接引用搜索排除一切别名或异常越界写。

EMPEROR主动出战4ABD7..4AC28：选中官员person+2设4，person+0取low8(counter)，B+6FC取完整word，counter++，B+6FE=FFFF。不论该战有多少普通兵队，只耗一个序号。属地受袭80D0B..80DA7按(local+43)武官、(local+13)文官两次查职务配置，各耗一个序号。slot数量45、官员总数、待处理战数与这项累计计数并非同一量。

原官员构造2EC2E将person+0置FF。原结算667AF..6680A只恢复person+2的状态，并未把person+0恢复FF或减少全局计数。原battle append 4AD32..4AD8D走到链尾追加，无计数<255限制；存档战斗记录数只有u8属于序列化当前链长度，与持续完成/清除战斗后的累计关联计数不同。

## 正常可达条件及边界

从初值c0的存档开始，A次已确认主动出战、D次已生成属地受袭：counter=(c0+A+2D) mod65536。只有创建确认走到上述配置块才计数；取消菜单、单纯进入战场、每队行动、普通结算清链不计数。第一个255关联在累计分配次数达到256时出现；256关联在第257次分配出现（初值0）。128次受袭会分配254/255，下一次受袭会分配256/257；255次主动出战后，下一次受袭分配255/256，同一场就含两边界。

这些不是必须同时排队256场，也不要求拥有256官员或256国家。结算理由1/3/4恢复官员可用状态并清战斗状态，允许重复使用同一官员和未吞并外国；因而地图仅30外国不能推出总战数最多30。重复开战再撤退/停战是正常路径上的累计模型，但尚不能据此宣称已无修改器玩到第257次：外交可再次开战、兵员/资源/寿命/行动消耗与对手行为须由完整菜单运行核实。建议主线用原菜单至少完成两次同目标循环确认可复用，并用原创建配置块+原结算连续运行257次验证累计性质；必须区分这两种证据。

## 查找和实际影响

66722/66762将B+6FC/6FE **符号扩展s16**，与官员person+0 **零扩展u8** 比较。

- 0..254：正常唯一分配期可匹配原官员；若人为制造重复byte仍先匹配链首，代码不另查出战状态4。
- 255：未分配官员默认FF也等于255。按链首顺序可能匹配无关官员；即使全部旧官员已分配，历史255若未再次出战覆盖仍会冲突。并非255一定失配，也并非255一定崩溃。
- 256..32767：person只保留低byte，正word值>255，不可能匹配任何合法person byte。
- 32768..65535：s16值负，也不可能等于0..255。65535并不等于默认FF；byte255零扩展为正255。
- u16溢出回0后又可匹配byte0，但已经存在其他低byte历史关联的碰撞风险。

退却/条件停战/普通兵耗尽（理由1/3/4）的非属地结算首个危险点667C0：读取node[0]，node已0；随后667C2写person+2=0。属地同分支667DE读第一node，667FF读第二node。吞并理由0/2的B胜路径对应66921读第一node（属地还会6693F/66960）；丢地路径会先free官员payload，再删除官员节点，两关联相同可能造成双重释放。255错配可把无关官员状态恢复或删除，实际将领仍保持出战状态4，影响后续任官/再出战；准确分支由结算理由和本地战标志决定。

**不要把空解引用直接写成已经证实SIG或必然立即退出。** 在32位DOS extender中线性0是否映射及其内容决定读0后发生什么；可能读取低内存，再在写入、free或链删除时损坏状态/异常。主线应在上述危险点断下记录node0、线性0 dword、后续EAX，先备份DOS状态，再连续执行真实结算直到原返回、DOS4GW错误或其他可观测终点，不替换函数也不跳过free。

推荐255动态例：真实官员链至少两个，前者FF且不出战，后者经原创建关联255；理由1结算观察前者state被恢复而后者仍4。随后用丢地理由0/2看删除的是谁，只在可恢复副本中执行。256例应保留真实原关联值256，完整结算无需人为改byte或强行造不存在ID；检查第一次空node读的实际影响。
