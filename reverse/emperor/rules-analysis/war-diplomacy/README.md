# 外交、贸易、战争：静态规则恢复（EMPEROR）

本报告的地址全部是 `EMPEROR/object1.relocated.asm` 的静态 VA，数据对象基址 0xb0000；不能把 KING 的同数字地址移植到 EMPEROR。函数边界和调用者来自启发式索引，真正的公式证据是逐条指令。已生成 22 份聚焦汇编、可重生成 `evidence.py`、可执行公式 `formulas.py`、数据表与调用者 `evidence.json`。没有运行游戏；公式样例验证的是重建模型，不能冒充原程序动态验收。

`T(x/y)` 表示 x86 IDIV 向零取整。以下公式适用于正常范围；原程序不少 word 算术会溢出，修改器极值不能套用普通数学无限精度。

## 地区对象与存档字段

每条内存地区记录步长 0x151=337。下列“相对偏移”以统治字段所在位置为基准，即 EMPEROR `0xc99ae + i*337`。完整运行时对象指针 R=0xc99ac+i*337，前2字节为外部index前缀，因此本报告偏移统一为 **R+2之后的字段基准**；换成对象R相对偏移时一律+2。绝对地址最可靠。原有 KING load mapping 不能直接用于这里的 EMPEROR。

|内存相对偏移|EMPEROR 字段 VA（i=0）|意义|宽度与置信度|
|---|---|---|---|
|0x00|0xc99ae|统治/归属判定，0=非统治|word，汇编；修改器只写低byte|
|0x20|0xc99ce|地区可用士兵|signed word，汇编+修改器|

## 友好度、关系分级和战争状态

`0x48eae` 处理友好度增减：正增量时累加后 `>=100` 写99；负增量时累加后 `<0` 写0。随后调用 `0x48f6a` 更新交涉对象的 byte+0x4f：

|友好度区间|分级代码|
|---|---|
|81..99|0|
|61..80|1|
|41..60|2|
|21..40|3|
|0..20|4|

具体中文态度名称需 UI 字符串进一步核对，不能只凭代码叫作“盟友/敌对”。

`0x4ac6b..0x4ad06` 是进入战争状态的明确写路径：关系对象 byte+0x1e 写5、全局国别状态数组同样写5，友好度 `T(F/2)`，贸易年数、额度、利润率、利润全部清0。因关系状态5在贸易结算中被排除，能确定它表示阻止贸易的战争状态。

低国家威望事件分支 `0x801ff..0x8040a`：皇帝状态 word+0x2b8<20 且一次性标记 word+0x2d0=0 时激活；遍历非统治地区并排除状态3，按 `random%100 < 100-F` 挑选，入选友好度减10且最低0；入选国家相互关系矩阵置2。若至少两个国家入选触发后续事件。因此友好度较低的国家更容易卷入这次联合行动。状态2的精确中文名、事件发起者与威望UI标签仍需字符串/动态确认。

概率辅助 `0x8a7fe` 明确为 `random%100 < threshold`，阈值本身没有在该函数钳制；正常PRNG非负时阈值>=100必成功。

## 贸易结算与增长

`0x12edd..0x13059` 对30个地区循环，只处理 `统治字段==0 && quota!=0 && relation_state!=5`：

```text
profit_rate = min(50, profit_rate + T(friendship/20))
income = T(quota*profit_rate/100)
if income>=0:
    emperor[0x4d] += income      # 收入分类账
    emperor[0x45] += income      # 资金总账，名称结合总字段表
else:
    emperor[0x71] -= income      # 亏损分类账（减负数即增加支出）
    emperor[0x45] += income
```

利润率是**累积**字段，最高50。F=79每次增长3，F=80增长4；quota=1000、初始rate=10、F=79则更新后rate=13、利润=130。友好度0..19没有增长但仍按已有rate结算。没有发现 rate 的最低0钳制，初始利润率就是-20（构造函数0x3ad42写R+0xb6=0xffec），因此初期亏损是正常设计。额度1000、友好99且保持不变时，前四次利润依次为-160/-120/-80/-40，第五次0，第六次40；这是固定友好度计算示例，实际友好度还会随关系年增长。

`0x133e0` 与皇帝年龄、官员年龄同时递增的年更新函数，对所有 `统治==0 && quota!=0` 的贸易年数+1；这里**没有排除战争状态5**，正常游戏由宣战清额度防止它递增。

交涉成功率候选 `0x473d1..0x47459`：

```text
threshold = T(F*F * T(emperor[0x2b8]*dialog[0x54]/dialog[0x58]) / 10000)
```

接着用上述概率辅助判定。dialog[0x54]=中国军力指标（皇帝+0x2cc），dialog[0x58]=对方军力指标（地区R+0x12f，即VA0xc9adb），在0x46b35..0x46b5c赋值。这是条约交涉成功率基式，具体四种见外交补充报告。这条路径对友好度是**平方影响**，且内层先整数除法，不可合并为一个浮点表达式。`0x47836..0x47846` 证明交涉类型2将用户提案参数写入贸易额度。

## 战斗临时数据结构

战斗对象含两个45槽数组，每槽18字节。side A record0 在+0x65，side B record0在+0x3ce（+0x369=45*18）。部分循环从slot1开始，slot0是特殊槽，不能随意当普通士兵。

|槽内偏移|类型|用途与证据|
|---|---|---|
|+0|byte|初始化标志，0x84a5a|
|+1|byte|兵种0/1/2；0xff=空，0x84a73|
|+2|byte|所属地区索引，0x84a47|
|+3|byte|本次未解|
|+4|i16|兵员数量，0x84a8b|
|+6|i16|头盔数，0x85684|
|+8|i16|皮甲数，0x8573b|
|+10|i16|皮盾数，0x857f2|
|+12|u8|训练，0x84aaf复制地区低byte|
|+13|i16|攻击值，0x859dc|
|+15|i16|防御值，0x85c2f|
|+17|u8|特殊作战标记，值1时部分伤害系数85；具体UI名称未解|

这些是**可持久化的战斗数据**。父级存档追踪证明load_other为1793字节序列化record，先分配0x704=1796内存并调用constructor，随后两次各读810=45*18字节到runtime+0x65/+0x3ce（KING0x9370a/0x937ed）；因此这两个unit数组直接持久化在other_records。原有三份存档该列表为空，没有真实在战存档动态样例；可用合成结构测试验证解析/无损回写。建unit时从地区士兵库存立即扣除本队兵员（0x84a22），出战数量与地区库存有实际转移。

攻击公式 `0x85942`：

```text
attack = 250 + T(12*N*(100 + T(training*100/30) + T(side_commander*100/240))/1000)
```

side A读取战斗对象word+0x393，side B读取word+0x391；作为统帅/阵营能力项直接进入公式，具体属性名称需查构造赋值链。不是所有兵种各自有独立攻击系数；兵种主要在相克表影响伤害。

防御公式 `0x85bac..0x85c2f`（side B本地实际装备队）：

```text
defense = T((25*helmet + 45*armor + 30*shield)/N)
```

满装全部为N时防御100；空装为0。这解释了装备数量和兵员数之间的比例。其它/援军队直接从地区+0x88复制预置防御，装备数清0（0x84af2..0x84b39），不能用满装公式反推所有队伍。

装备分配时头盔/甲/盾分别 `assigned=min(stock,N)`，每项都从地区库存扣减，按slot顺序供给，先排的队伍可能拿走全装备。地区+0x13a的工事项直接缩放特定一侧伤害，为战术之外的第二层防御。

## 实际战斗损失公式与相克原始表

`0x59437` 为行动触发的结算函数；损失公式连续位于 `0x5954d..0x59969`，之后调用单位消灭/伤亡/UI反馈函数，并在 `0x59c03/0x59c1f` 扣双方兵数。

设A队/B队攻击为ATa/ATb、防御为DFa/DFb：

```text
LA=max(0,T((10*ATb-25*DFa)/130))
LB=max(0,T((10*ATa-25*DFb)/130))
C=500-region[0x13a]
S=85 if relevant_unit.special==1 else 100
if acting_side==1: LA=T(C*LA*S/50000)
else:              LB=T(C*LB*S/50000)
```

这里工事和special只缩放**一个方向**，不能把它们平均乘到双方。C读A来源地区或B来源地区，取决于 battle byte+0x12；实际指令在0x5960f/0x5963c。原局部C先初始化1000但紧随分支两边都会覆盖；正常路径C不是1000。

非slot0战斗再读取九字节兵种相克表（VA 0xc80d8）：

|损失方type行 / 施伤方type列|0|1|2|
|---|---|---|---|
|0|100|75|115|
|1|115|100|75|
|2|100|115|75|

```text
LA=T(LA*table[3*typeA+typeB]/100)
LB=T(LB*table[3*typeB+typeA]/100)
```

**保留原始表的非对称与type2同型75**，没有擅自修正为常见循环相克。依据库存刀/枪/马的供兵分支，type0/1/2高度可能对应刀兵/枪兵/骑兵，但尚缺直接UI文本证据，模型只用数字type。

随后双方损失不超过当前兵员N。如果只有一方原拟损失>=N，它造成的另一方损失会减少 `T((原拟损失-N)/3)`，最低0；双方均达消灭条件则双灭，不走该保护。这是“过量伤害”修正，不等于把两边各简单min到N。

实际数值：100兵训练30、阵营项120 ->attack550；满装 ->defense100。100兵训练20、阵营项80 ->attack488；半装 ->defense50。相克type0对type1且A行动、工事100，模型得到A损失10、B损失36。`formula-examples.json` 给出更多结果。

## AI估算和实际结算差异

`0x62905` 读取同一攻击/防御、同一相克表，带坐标参数并最终返回估算值；依据调用形式与没有在这段直接扣兵判断是AI候选模拟路径（不能替代实际伤亡公式）。

与 `0x59437` 不同，0x62905没有在raw损失计算后做非负钳制；它对双方都乘工事/special系数，并先乘相克一次、消灭保护后又乘同一相克一次（0x62b72与0x62d4f、0x62bcf与0x62da8）。此外0x62c69取B兵数时使用e0(A槽号)，后续0x62cb0改用e4(B槽号)。这是静态观察到的代码差异/疑似bug，**尚不能证明游戏表现中必然触发**。该路径不能用整洁公式替代，完整指令保存在ai_battle.asm。

## 兵员/库存分配与上限

`0x84f54` 将刀、枪、马库存三类作为可供编队量；分母 `Q=min((刀+枪+马的word结果),4500)`。

- 若士兵N>Q，将三种库存数全部转为三类出战数并清库存；这一分支存在仅对Q钳制、出战数量仍用原库存的细节，异常修改器值可能使之超过4500。
- 否则三类 `out_i=T(N*stock_i/Q)`，扣对应库存；士兵若>4500先压4500，按三类出战数得到剩余，尾数再按刀→枪→马轮流补足。
- 三类单位以最多100人的小队生成，最多45槽；外援数量以 `T(population*region[0x140]/100)` 算出，并分成三类。单侧辅助生成 `0x85273` 先对随机20%区间减半或20%区间减到1/4，再上限4400，三类均分再每100人分队。

上述4500是这条兵员选择路径上限，不能宣称为游戏所有兵数或全局战斗最大人口。slot0/援军/其它构造路径需要分别核查。
